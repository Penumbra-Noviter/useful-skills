# Research 调研坑

从个人知识库 `demo/经验/` 蒸馏的调研期坑。写 findings 前先读；每条给「反模式 → 正解 → 验证点」，来源见知识库同名笔记。

**维护约定（防双源漂移）**：经验本体在知识库 `demo/经验/`，本文件是面向子智能体的缓存副本，知识库为唯一权威。每次 `distill-lesson` 蒸馏新调研坑后顺带核对本文件；冲突时以知识库为准重写。

- **参考实现的实证结论只能当假说**：引用开源/外部项目的「实测结论」进 findings 时标注「待本机复验」，不把他人实证当自身实证。该结论要落地成实现时，把高不确定点前置为 spike，而非直接写进 spec。（`参考实现的实证结论必须在本机复验`）
- **调研第三方 API 先抓真实响应**：请求头、凭证握手、响应 schema 三环都不能凭文档想象。第一条动作是抓一份真实响应存 fixture，用真实数据驱动后续解析；手写 mock 通过 ≠ 集成成功。（`第三方 API 集成先抓真实响应`）
- **findings 不得复制被审逻辑当结论**：复述外部代码/结论时保留来源与「未复验」标记，不把复制来的逻辑当成自己验证过的结论——复制品与原件漂移后，自检永远「通过」。（`审计工具不能复制被审代码`）
- **LLM 结构化输出三级兜底**：解析 LLM 返回的 JSON 用「直接 loads → 提取代码块 → 花括号截取」三级 + 白名单字段过滤 + 类型容错；字段约束在系统侧，容错在解析侧。（`LLM 生成 JSON 三级提取策略`）
