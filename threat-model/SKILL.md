# 威胁建模（STRIDE）

## Overview

在实现前对一项功能做 STRIDE 威胁建模，把「哪里会被攻击」转成「实现时必须满足、且能在 code-review 与 pytest 里验证的安全需求」。目标是让安全要求成为工单的 acceptance criteria，而不是事后补救。

## Resource Guide

- `references/stride-fastapi.md` — STRIDE 六维的 FastAPI + SQLAlchemy 2.x + Pydantic v2 语境化威胁表与安全需求映射。在 Workflow 第 3 步跑六维时加载。

## 触发判定

先判定是否建模，避免对无风险面的脚本套仪式：

- 命中任一高风险面 → 建模：认证/授权与权限边界、外部输入（HTTP 参数、文件、消息队列）、密钥或凭据的存取、持久化与数据迁移、加密或签名、第三方集成、文件上传下载、多租户或越权访问。
- 全部不命中 → 跳过，输出一行「无高风险面，跳过威胁建模」。
- 一次性小工具、无输入无持久化的纯脚本 → 默认跳过，除非用户明确要求。

## Workflow

1. **圈定范围与资产**。列出功能涉及的数据、凭据、外部依赖与信任边界——标记每个不可信输入的进入点。完成标准：每条资产都标注密级（公开/内部/敏感）与归属组件。
2. **枚举数据流与攻击面**。沿每个外部入口到存储或出口走一遍，标出信任边界两侧。完成标准：每个入口点能说出它从哪来、写往哪去。
3. **跑 STRIDE 六维**。对每个攻击面依次过 Spoofing/Tampering/Repudiation/Information Disclosure/Denial of Service/Elevation of Privilege，加载 `references/stride-fastapi.md` 按 FastAPI 语境逐条对照。完成标准：六维都过完，每维 0 个或多个具体威胁，无「用加密」这类空泛结论。
4. **产出安全需求**。把每个威胁转成一条可验证需求，说清「用什么、在哪、怎么验」。例：「所有 DB 查询走 SQLAlchemy 参数化，禁止字符串拼接；验证点——review 检查无裸 SQL + pytest 注入 payload 返回 4xx 而非 500」。完成标准：每条需求都能落到 code-review 的 Falsify 轴或一个 pytest 断言。
5. **交回给 kick 流程**。把需求清单作为该工单的 acceptance criteria 写入，供实现与 review 使用。完成标准：需求清单定位到工单，不是孤立文档。

## 输出契约

```markdown
# 威胁模型：<功能名>

## 范围与资产
| 资产 | 密级 | 归属 |

## 信任边界
<每个不可信输入进入点及边界两侧>

## STRIDE 六维
| 维度 | 威胁 | 风险 | 缓解（安全需求） |

## 安全需求（可验证）
1. [ ] <需求> — 验证点：<具体断言或 review 检查>
```

每条安全需求用可证伪措辞：能说出「什么输入/状态会让它失败」。

## Boundaries

- 不做渗透测试或漏洞利用；只做设计期的结构化风险识别。利用类请求按安全研究场景走。
- 不评审整仓安全，只针对当前工单或功能的范围。
- 不产出合规声明（PCI/HIPAA 等），除非用户明确要求该合规域。
- 不替代 code-review 的 Falsify 轴：威胁建模产出需求，review 验证需求。

## Quality Standard

- 每条需求都可验证：review 能 cite 行号检查，或 pytest 能写断言覆盖。
- 六维都过完，没有用空泛词（「用加密」「做好校验」）收尾的需求。
- 风险分级诚实：能说出 exploit 触发路径的才标高风险。
- 无高风险面时明确跳过，不制造模型。
