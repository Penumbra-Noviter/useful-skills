# 因果链追踪 (Root Cause)

## R — 原文 (Reading)

> "B确实是导致C的直接原因，但它不是根本原因。因果链的源头是A，因此A才是造成问题C的根本原因。……除非根本原因A得到足够的关注，否则C的问题就不能得到有效解决。"……"一件事恰巧出现在另一件事之前，这并不足以断定它们之间必然有因果关系。"
>
> — D.Q. 麦克伦尼，《简单的逻辑学》第2章·04 对原因的探寻不要半途而废、第5章·24 以先后论因果

---

## I — 方法论骨架 (Interpretation)

现象 C 只是链条的末端。紧挨着它的 B 是直接原因，但 B 自己也是结果，链条往上还有 A（根本原因）。停留在一层解释，就是萨姆不停倒掉臭水桶。

核心五步：

1. 描述问题现象 C，限定到可观察、可复现的单一问题。
2. 画因果链：对 C 连问"为什么"（为什么-为什么追问），先找到 B，再追到 A。
3. 验证 A 有能力造成 C——从果溯因：原因必在结果上留印记，候选原因必须"有能力"产生该结果（蚂蚁太轻打不翻奶瓶，邻居的猫可以）。
4. 修 A，而不是反复处理 B：只处理 B，问题根源还在原地嘲笑。
5. 时间先后只作嫌疑、不作证明：鸟鸣先于日出，但不导致日出；只有先后信息时，结论只能停在"可能是原因"。

原因内部再加一层区分：主要原因（决定问题存在的最终因素）优先于工具原因（实现目标的媒介）——先保证主要原因合格，别在工具上打转。

交付物：一条从 A 到 C 的可复述因果链（每一段都有机制，不是时间表）+ A 的干预方案。

## A1 — 书中的应用 (Past Application)

### 案例 1: 摔碎的牛奶瓶与邻居的猫
- **问题**: 桌上的半瓶牛奶摔碎在地，看不到"凶手"
- **方法论的使用**: 从果溯因——按结果的印记逐一评估候选原因的能力：蚂蚁太轻不可能带来如此重量级的结果、金丝雀无力，邻居的猫有能力
- **结论**: 猫是重点嫌疑对象；不能肯定就是它，只能列入嫌疑
- **结果**: 用"原因必在结果上留印记"把候选缩小到有能力者的范围，再继续观察验证

### 案例 2: 萨姆与厨房臭水桶
- **问题**: 水槽下盛满臭水的桶，倒掉后一会儿又满了
- **方法论的使用**: A→B→C——倒水处理的是直接原因 B；再问"B 又由什么造成"，追到漏水管 A
- **结论**: 修好漏水管才是根治；只倒水，问题的根源还在原地嘲笑
- **结果**: 治标不治本被示范为无效；根本原因得到关注前，问题不能得到有效解决

### 案例 3: 原始人与鸟儿歌唱
- **问题**: 鸟儿总在日出前歌唱，是不是鸟鸣导致日出
- **方法论的使用**: 只用时间先后信息时，把"先发生"当作嫌疑而非证明；追问机制，需要更多信息
- **结论**: 鸟鸣与日出之间没有因果机制；最好的结论只是"先发生者可能是原因"
- **结果**: 以先后论因果被识别为谬误；因果判定必须要求额外证据

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 线上故障/代码缺陷"修了又犯"，补丁打了一层又一层
2. 业务指标（留存/转化/性能）持续下滑，团队急着给表面解释
3. 事故复盘/归因争论，有人拿"先发生"当因果证据
4. 慢性流程/组织问题（污水桶式），反复处理症状
5. 调试现场只见现象不见原因，需要系统排查

### 语言信号 (用户的话里出现这些就应激活)

- "又出问题了"
- "上次修了怎么又犯"
- "根本原因是什么"
- "这事怪谁"
- "为什么老是这样"
- "It broke again" / "Why does this keep happening?" / "What's the root cause?" / "Who's to blame?"

### 与相邻 skill 的区分

- 与 `fallacy-detector` 的区别: 以先后论因果（事后归因）是谬误识别器诊断的因果分支；本 skill 是正向追因程序，一个是防御、一个是进攻
- 与 `fact-confirmation` 的区别: 事实确认核查"某命题是否为真"；本 skill 在事实已确认后追问"为什么会这样"
- 与 `conditional-argument` 的区别: 条件论证评估"如果 A 那么 B"的论证结构；本 skill 处理真实因果链的追溯，不依赖形式化命题

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **描述现象 C**
   - 完成标准: 一句话写清"什么现象、何时开始、什么条件下复现"；现象含糊就先拆分到可观察粒度
   - 判停条件: 若是一次性且修复成本极低的简单故障，直接修复，不进入根因分析

2. **画因果链 A→B→C**
   - 完成标准: 每推进一步都写出机制说明（B 通过什么导致 C、A 通过什么导致 B），链上不允许只有"先发生/后发生"关系
   - 判停条件: 若追问 2-3 层后所有候选链都只有时间先后而无机制证据，停止宣称根因，结论降级为"可能是原因"并列出证据缺口

3. **验证 A、修复 A、观察回归**
   - 完成标准: 验证 A 有能力造成 C（结果印记匹配；必要时最小实验证伪），干预落在 A 而非 B，并在完整观察期内确认 C 未复发；复发则回到步骤 2 重画链

**输入契约**: 调用本能力需要有可观察、可复现的问题现象 C，至少包含"什么现象、何时开始、什么条件下复现"三要素；若用户只给了笼统抱怨（"又出问题了""指标掉了"）或缺复发证据，应先询问现象的具体表现、起始时间、复现条件，以及此前是否已做过处理。

**输出契约**: 交付一条从 A 到 C 的可复述因果链（每一段都有机制说明，不含纯时间先后关系）+ 对 A 的干预方案与回归观察结论；若链条未能通过机制验证，结论降级为"可能是原因"，并列出证据缺口与后续验证路径。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 大样本统计归因（A/B 实验、观察性数据）：单靠逻辑链不够，需要对照组、效应量与置信度；此时根因结论是统计性的，不是演绎性的
- 预测未来行为：因果链解释过去 ≠ 预测未来；弱条件预测请走条件论证评估
- 高复杂多因系统强行找"唯一根本原因"：可能过度简化，需接受多因并存与交互因素

### 作者在书中警告的失败模式

- 以先后论因果（ce24）: 鸟鸣先于日出不等于导致日出；"自从……之后"句式不构成因果论证
- 因果探寻半途而废（ce45）: 找到直接原因就收工，萨姆倒水式问题反复发作
- 肯定后件（ce02）: 结果成立不锁定单一原因——"他成功了所以方法一定对"跳过原因排查

### 作者的盲点 / 时代局限

- 必然性理想：作者的四因论/因果链是确定性框架，但软件、市场、社会等真实系统是概率性、多因交互的，把"唯一根本原因"当必然目标会漏掉交互因素
- 把追因失败归于个人懒惰与耐心不足，忽视结构性因素——利益驱动的信息环境会系统性隐藏真实原因链（算法、宣传、组织激励）
- 朴素实在论："原因在结果上留印记"对物理世界直观，但对抽象系统（留存下降、组织问题）没有可直接观察的印记，验证手段更间接

### 容易混淆的邻近方法论

- 相关分析: 相关性 ≠ 因果，需要机制与排除替代解释（本 skill 第 5 步正是为此）
- 5 Whys: 同源方法，但容易停在人为选定的"为什么"上；本书补充了"从果溯因"以验证候选原因的能力
- 四因论: 作者的四因分类（动力/质料/形式/目的）因验证未过（V1 未过）不独立成 skill，本 skill 只取其中"主要原因 vs 工具原因"的分层；完整四因论见候选素材，勿直接混入根因流程
