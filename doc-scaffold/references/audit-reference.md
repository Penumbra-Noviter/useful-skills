# 文档体系审计参考 — 档位判定 / 文档角色 / 范式提取

> 配套 `SKILL.md` 的 Workflow 使用。规则唯一权威 = 用户全局 AGENTS.md（`C:\Users\Administrator\.zcode\AGENTS.md`）§3 任务清单生命周期、§3.5 知识库闭环、§3.6 文档体系档位制；本文件为操作速查，不复制规则正文。

## 一、档位判定（标准档 vs 完整档）

| 档位 | 必配文档 | 升档条件（全部满足才完整档） |
|------|----------|------------------------------|
| 标准档（默认） | `AGENTS.md` + `PROJECT_REFERENCE.md` + `TO-TICKETS.md` + `DEV_LOG.md` | — |
| 完整档 | 标准档 + `CODE_WIKI.md` + `scripts/doc_sync.py` | 模块数 ≥ 8 **且** 文档 > 1 页 **且** 多场景引用（新人/Agent/review） |

判定步骤：
1. 目标项目已有 `CODE_WIKI.md` → 直接完整档。
2. 否则数核心模块（`src/` 或包内模块文件数 ≥ 8）且文档已 > 1 页 → 完整档；小工具（单文件脚本、模块 < 8）→ 标准档。
3. 拿不准时按下限处理：标准档起步，文档体系长出来再升（升档是加 CODE_WIKI + doc_sync，不推倒重来）。

## 二、文档角色速查（建什么、谁管什么）

| 文档 | 角色 | 唯一来源（只归它管） |
|------|------|------------------------------|
| `AGENTS.md` | 行为规矩（标准档必配） | 项目模式判定 / 任务池生命周期 / 文档体系档位 / 知识库路由 / 编码惯例。**一律命名 AGENTS.md，不建 CLAUDE.md** |
| `PROJECT_REFERENCE.md` | 项目介绍（标准档） | 一句话定位、技术栈、目录约定、当前状态、关键决策。**不复制技术细节** |
| `TO-TICKETS.md` | **唯一任务池**（标准档） | 已立项/在执行的工单 + 已完成归档。待办**绝不落** DEV_LOG / memory / 个人笔记 |
| `DEV_LOG.md` | 已做 + 叙述（标准档） | 完成记录、来源/Grilling 共识/验证链/过程遥测、bug 根因。只记「已做」 |
| `TECH_DEBT.md` | 技术债候选池 | 未立项候选（编号/来源/强度/状态/归属方向）+ 复核关闭表 + 处置记录；不自动进入 preflight |
| `CODE_WIKI.md` + `scripts/doc_sync.py` | 完整档（升档后） | 技术细节单一权威源 + 代码导览（兼 CODE_MAP，**不另建 CODE_MAP**）；机械标记防漂移 |
| `CONTEXT.md` | 领域词汇 | load-bearing 术语登记，供架构评审/设计/编码统一使用 |
| `KNOWLEDGE_BASE.md` | 知识库路由 | 所属 vault / 项目页 / persona / 经验路径（双库路由查表入口） |
| `README.md` | 用户视角 | 安装、CLI 用法、技术栈、目录约定、当前状态 |
| `MANUAL.md` | 用户手册 | 面向终端用户的完整操作手册（可选，GUI 项目常配） |
| `CONSENSUS.md` / `docs/adr/` | 需求 + 架构决策 | 需求定义 + ADR 决策记录（项目二选一：内嵌 CONSENSUS 或独立 docs/adr/） |
| `DOCUMENTATION_STANDARDS.md` | 文档规范总表 | 各文档角色/单一事实来源/滚动约定索引。**同一信息只存一处，其余引用** |

## 三、范式提取步骤（读 reference 目录时）

1. 优先读 `reference/DOCUMENTATION_STANDARDS.md`——它直接给出文档清单、单一事实来源分配、滚动约定、门禁表，是最高信噪比范式。
2. 没有总表时：读 `reference/AGENTS.md` 的「文档分工与状态」表 + 根目录 `.md` 清单，归纳出该项目的文档家族。
3. 提取要素（只提取，不复制叙述）：
   - 文档清单：哪些文档、各自角色/唯一来源
   - 格式约定：DEV_LOG 滚动（倒序/折叠）、TO-TICKETS 归档（每批一行/索引上限）、TECH_DEBT 清出（候选区只留开放/处置记录滚动）
   - 机械门禁：用了哪些检查脚本、挂在哪（pre-commit）、档位
4. 差异适配：目标项目与范式项目的规模/技术栈不同 → 只吸收结构，不照搬具体内容（如测试数、模块名单、批次历史全部丢弃）。

## 四、机械门禁速查

| 脚本 | 职责 | 依赖 | 分发档位 |
|------|------|------|----------|
| `pool_cleanup_check.py` | TO-TICKETS/TECH_DEBT 清出机制（候选区状态/复核关闭/活跃表无 ✅❌/归档索引 ≤60/脚注编号一致/必要节/表格列数异常） | 纯标准库 | 任何档位 |
| `doc_sync.py` | CODE_WIKI 机械标记（tests_total/模块行数/方法签名/文件引用双向覆盖） | pytest（收集测试数） | 仅完整档 |
| `doc_standards_check.py` | 文档规范总表（清单表格式/登记双向覆盖/门禁脚本存在/pre-commit 挂载） | 纯标准库 | 总表一经建立即装 |

pre-commit.sh 档位自适应：`[ -f CODE_WIKI.md ] && python -c "import pytest"` 才跑 doc_sync——标准档项目无 CODE_WIKI.md 自动跳过，模板无需运行时修改。
doc_standards_check 门禁脚本存在性同样档位自适应：标准档项目（无 CODE_WIKI.md）门禁表引用 `doc_sync.py` 时豁免其存在性——模板门禁表可原样复制，无需按档位删行。

## 五、常见偏差与处置

| 现象 | 处置 |
|------|------|
| 目标项目已有 `CLAUDE.md` | `git mv` 改名 `AGENTS.md`（保史），文档内引用同步；DEV_LOG 历史条目保留原词（记录当时事实） |
| 目标项目已有文档但分工表不全 | 核对各文档职责声明，补分工表行；不重写已有内容 |
| 目标项目无 `.git` 或无 `scripts/` | 说明是脚手架场景（未初始化/纯脚本目录），建文档可继续；pre-commit 挂载标注「待 git init 后执行」 |
| 目标项目已有同名检查脚本 | 先 diff，若为同源通用版则保留；内容漂移则按模板覆盖（备份旧版） |
| 目标项目模块 < 8 但用户要完整档 | 尊重用户显式要求升档，但报告里标注「按档位判定为标准档，已按用户要求升」 |
