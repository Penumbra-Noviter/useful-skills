# Trust 边界（trust-boundaries）

用户约定的边界，最高优先级。执行态度**开放**（采集按"方法可行性"、逆向按"能力以内"），但在触碰目标前有一道**自动化授权预检**兜住法律红线。

## 采集侧（crawl）

- **可行即采**：一切从方法可行性出发**可以爬取**的数据都尝试采集——不因"看起来难"而预设放弃，能采到的就采。
- 手段以"方法可行性"为上限：选型、反爬回退、逆向反爬机制都以能采到为目标推进。
- **不压垮目标**：不做拉满并发的压测式采集，注意频控与礼貌。
- 采集到的数据，其**使用**不侵犯他人合法权利（隐私、著作权、商业机密等）。

## 逆向侧（reverse）

- **能力即做**：一切**能力以内**可以逆向的目标都逆向——只要是能力所及就推进分析。
- 沙箱执行安全（这不是授权门槛，是防误伤的执行安全）：操作副本不碰原件；不执行未知样本；不外部服务。
- 模糊目标（破解/解锁/绕过/拿 flag）先归一化为逆向目标，不预设拒绝。

## 自动化授权预检（兜红线的执行层）

采集/逆向前，对目标跑 `scripts/check_target.py`（详见 `references/authorization-check.md`）：

- 对 URL：检查 robots.txt 是否禁止、无凭证 GET 是否 `401/403`、是否重定向到登录墙——**登录墙是"受保护数据"最可自动化的信号**。
- 对本地样本：检查路径是否存在、来源是否用户自持。
- 判定：`ALLOW` → 继续；`CHECKPOINT`（命中登录墙/鉴权/robots 禁止/来源不明）→ **停下让用户确认**；`BLOCK` → 停止。
- 职责：**在触碰红线前把它摆到用户面前**，不是设死门槛。用户确认后仍按"方法可行即可采/能力以内即做"推进。

## 红线（不可跨越）

- **不违背法律采集受法律保护的数据。**
- 具体某份数据是否"受法律保护"，由使用方自己判断并承担——skill 不替你做法律定性，但一旦触及该红线即停；自动化预检负责把高风险信号提前呈报。

## 工程安全

- 凭证、Cookie、私有绝对路径不入代码/公开产物；走环境变量或配置。
- 采集与逆向的 case 工作区与原始产物分离；逆向操作副本。
- 外部行为（发布、部署、向第三方发送）需显式授权。

## 判定顺序

1. **Step 0 授权预检**：跑 `check_target.py`。
   - `ALLOW` → 下一步；`CHECKPOINT` → 停下请用户确认；`BLOCK` → 停。
2. 用户确认后（或已 ALLOW）：采集按"方法可行性"，逆向按"能力以内"，全力推进。
3. 执行中若新发现受保护数据信号 → 回到 Step 0 重新判定。
